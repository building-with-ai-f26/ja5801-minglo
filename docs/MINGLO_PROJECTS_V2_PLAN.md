# Minglo Projects workspace release plan

**Status:** Proposed for implementation. Reviewed November 23, 2026 on main at `1038fe9`. The released application baseline is Heroku v59, source `dc468e4`. This is a product and engineering handoff. Implementation, external invitations, infrastructure changes, and production release each follow the owner's instructions for that work.

## The release to build

A person brings a goal and a deadline. Their team turns it into an editable work plan, splits up the work, asks each other questions, reviews real outputs, and hands the person a finished package they can use outside Minglo. A person working alone, a person working with one agent, and a team of people with several agents can all start the same way.

**The release demonstration is a workshop kit:** two people and two independently hosted agents produce a facilitator agenda, an exercise sheet, and a participant handout. Two tasks start at the same time. A later task uses the reviewed output from an earlier one. A human resolves an ambiguous requirement halfway through. The final delivery pins three named versions. The owner can inspect, approve, and download the kit. These are requirements of one release. The engineering batches below are integration points.

Keep Minglo’s explicit membership, exact-version human approval, stable return links, retry-safe writes, and independent host execution. Keep Home as the entry. A team can meet anywhere. Use Minglo’s Side by Side typography, surfaces, attribution, and themes for the new screens. Huddle’s timeline and simulated speed claims do not establish scheduling requirements here.

## What a team will do

1. **Kick off.** On Home choose **Start a project**. Give it a name, outcome, optional due date, and success criteria. Choose **Start blank** or **Use a workshop plan**. The latter previews three editable tasks with suggested inputs and reviewers before saving. The creator can start working immediately. Invite by searching public names and handles, with a shortcut to the creator’s own agents. Show pending invitations separately from joined members. Claiming or following an agent cannot enroll it.
2. **Agree on the work.** The creator assigns “Draft the agenda” to Agent A and “Design the exercises” to Agent B. Both can start today. A classmate takes “Write the participant handout.” Its input is a recommended exercise sheet. A member can propose an additional task or revised brief. The project lead sees the proposed changes together and can accept, edit, or decline them. Record the adopted plan and its author. A built-in starter is a template. An agent-authored plan must actually come from the invited agent.
3. **Take a turn.** Agent A signs in and opens **My work → Draft the agenda**. One page shows the outcome, assigned task, done criteria, relevant notes, input versions, and destination for its output. It accepts the assignment, saves a working draft, then submits **Agenda v1** for review. B’s exercise task continues independently. A context update or a new invitation elsewhere cannot invalidate either draft.
4. **Resolve a real blocker.** B asks “Can attendees work in pairs if the room has fixed seating?” and selects the workshop lead under **Needs an answer from**. B can mark its task **Waiting for an answer**. The lead answers beside the question. B returns to the answer from Home, even in a new session. This interaction is visible to current project members. Only the person asked gets a decision item. A normal comment creates no team-wide alert.
5. **Review and hand off.** The reviewer requests a specific change to Agenda v1 because the activities run 20 minutes over. A sees the exact comment and draft, submits v2, and adds a change summary. The reviewer compares v1 and v2 and recommends v2. When the exercise sheet reaches its agreed review requirement, the handout author gets **Start participant handout** with that exact sheet attached. Nobody pastes its contents into another agent’s chat.
6. **Deliver.** The lead opens **Prepare delivery**, selects Agenda v2, Exercise sheet v1 and Handout v2, and checks the success criteria. A missing review links to the affected version. The designated human sees **Approve workshop kit** with the three versions, outstanding questions, recommendations, and changes since the previous submission. Approval creates an immutable package. Members can copy the combined result, download a Markdown bundle, or print a clean handoff document to PDF. Later work may produce a second release. The original package stays reproducible.

## The workspace

| Surface | Primary interaction and content |
| --- | --- |
| **Projects** | Accessible from Home and More. Show **My work**, **Needs my decision**, and **Your projects**. Work and decision lists page independently, with pending invites and direct links to the exact task, request, or release. When a card drops off the Home preview the underlying action remains findable. |
| **Overview** | Show the outcome, lead, due date, next milestone, and one personal next action. **Since your last visit** names meaningful events and links to their sources. Below it, show work waiting on a person, ready deliverables, and the team. A first-time visitor sees setup actions. A returning member sees what changed. Derive this summary from recorded events. |
| **Plan** | An editable task list grouped by milestone. Each row shows who owns it, its due date, what makes it done, and the reason it is ready or waiting. Filter by **Mine**, **Ready**, **Waiting**, and **Completed**. Allow inline assignment and reordering with keyboard controls. A named milestone can group several tasks. Dates indicate scheduling intent and never advance work automatically. |
| **Task** | The assigned person or agent sees the work brief, reference material, dependency versions, a recoverable draft, submission control, version history, and task discussion. Reviewers see a readable before/after comparison and can attach a change request to a heading or the whole version. A stale tab retains unsent text and provides a comparison with current work. |
| **Outputs** | A project library of named documents with author, owner, current version, and review status. Support a Markdown subset with headings, lists and tables, plain-text editing, preview, and member-only copy/download. Project notes and labeled external links can be pinned as shared context. Links are references. The saved document contents are the approval subject. |
| **Decisions and delivery** | A human can see unanswered questions, requested approvals, and past decisions. Each request names the requester, person responsible, source task, and consequence of answering. A delivery opens with a short handoff summary assembled from its goal, included outputs, recorded change summaries, and linked decisions. A teammate can explain why the team changed the agenda and open the exact evidence. A delivery shows the frozen manifest, reviewers, outstanding requirements and final sign-off. Historical delivery links always open the versions actually accepted. |

Use one project navigation row inside the existing shell. On mobile show an accessible compact switcher, the current task or decision first, and optional history below. At desktop width use the extra space for inputs beside the active work or a reviewer’s comparison. Build clickable local pages with genuine fixture states before polishing. Verify phone keyboard navigation, light and dark themes, narrow widths, long names, empty teams, pending invites, and stale or revoked links.

## Work rules and authority

- **Membership and assignments are separate.** The human creator is the lead and default release approver. They manage membership, accepted plans, assignments, review rules, and packaging. Accepted human and agent contributors can own multiple tasks, propose work, submit their own assigned outputs, review other assigned work, and answer questions directed to them. Include an explicit read-only membership option. Existing v1 readers retain read-only rights. Invited accounts receive only the invitation envelope. Connected owners outside the project receive no project content, search results, or previews.
- **A task can start before the full team joins.** Its owner must be an accepted contributor, its recorded prerequisites must be satisfied, and any explicit blocker must be resolved. Show unassigned tasks and proposed assignments to pending invitees as waiting for staffing. An assignment, a participant explicitly starting, and an actual submission are separate events.
- **Readiness is a choice per task.** Support submitted, recommended, or human-approved output as the completion condition. A review requirement names a distinct reviewer. A human approval requirement names an accepted human. Direct submission can complete low-risk supporting work. Only the designated human can approve a final release. Translate these differences into user-facing labels.
- **Dependencies pin evidence.** Store prerequisite task, required readiness, and the output version that satisfied it. Reject cycles, self-links, and cross-project links. Multiple unrelated tasks may proceed concurrently. If an upstream version changes after a downstream task starts, show **New input available** with a comparison. Require the downstream owner to adopt the update or record why the previous input still applies before the next delivery. Never rewrite what an already approved package depended on.
- **Decisions have consequences.** Distinguish an informational comment, a blocking question, a change request, a reviewer recommendation, and a human approval. A named responder can answer a question. A lead can reassign it with attribution. Opening the page does not answer it. A changed deliverable or changed release manifest requires fresh review or approval at the affected level. A historical recommendation remains attached to its original version.
- **Define what prevents delivery.** Block final approval for any missing required output or unmet review, unresolved blocking decision on included work, or unacknowledged newer input. Show optional unfinished work separately. An informational comment never blocks approval. Editing a submitted package sends a new immutable manifest to the approver.
- **A release is a milestone; closing ends work.** Approving a release freezes that package while allowing later work. Closing ends writes and pending invitations, clears actionable queues and retains authorized history. Removing a member immediately revokes every project read and mutation, including attachments to context, exports, counts, and old direct links. Vacated work returns to the lead for reassignment. A new reviewer verifies the exact version before a pending approval can proceed.
- **Agent participation still belongs to the host.** Existing agent and connected-owner pause rules apply to contributions, reviews, answers, proposals, and automated project actions. Leaving remains available. Recheck blocks for invitations and directed handoffs. Where a handoff is unavailable, give the lead a replacement action without disclosing a private block. A delivery approval authorizes acceptance inside Minglo. External sending, spending, publishing, and host scheduling require their own authority.

## How to build it in this checkout

**Compatibility first.** The deployed schema stores phase, current version and accepted version on `Project`, and the working role on `ProjectMembership`. The version number is unique within the project. `changeProject` uses the project revision and row lock for almost every action. `getProjectReturns` derives a single turn from the phase. The catch-all project page renders several different jobs in one file. Adding tabs while keeping these assumptions will still give the team one turn. **Proposed records and ownership of state**

| Area | Proposed implementation |
| --- | --- |
| Team and plan | Keep project identity, creator, membership status and invitation generations. Add a workspace-format discriminator, project-level membership permission, task milestones, versioned brief, tasks, task assignments, readiness settings, and directed dependency edges. A plan proposal contains specific additions/changes and the brief/plan revision it was based on. Only adoption changes live work. |
| Work and output | Give each task an owner and optional reviewer/approver. A task produces one primary named deliverable. Several deliverables may be packaged together. Store an account-scoped working draft per task with a revision, immutable submitted versions, and pinned input references. Use optimistic revision checks for draft saving across tabs. A private working draft becomes member-readable at explicit submission. |
| Context and decisions | Project reference notes are versioned when pinned as inputs. Keep comments and questions scoped to their task or project, with optional exact-version and heading anchors. Store a decision’s type, requested actor, open/resolved state, resolution, time, and immutable subject. Review and approval must be checked against the exact submission or manifest being acted on. |
| Delivery and return | Store draft release manifests and immutable approved release items, each referencing a deliverable/version pair. Keep attributed project events with typed references and bounded cursor reads. Derive personal work from accepted membership, task readiness, and open decisions. A per-account project visit cursor powers catch-up and never clears pending work. Index actionable work by account and project, decisions by responder/status, and event reads by project and cursor. |

**Transaction contract.** Derive the actor from the session for every action. Use separate conflict checks for plan edits, task edits, draft saves, review decisions, and release manifests. A collaborator’s comment must not invalidate another task’s submission. Establish one compatible lock order for project access/revocation, directed block pairs, agent pause, and affected tasks/outputs/decisions in sorted order. Serialize dependency graph edits per project; validate readiness in the write transaction. Check membership and write authority again after locks. Insert a submission, its immutable event, consumed inputs and any new decision in one transaction. Enforce same-project references, stable per-actor operation keys with payload matching, one result per intended submission, and one final approval per manifest revision. A retry can return an existing receipt only to a still-authorized viewer.

**Migration path.** Use additive migrations and a format flag. First build a read adapter for v1 and fixture-test every legacy phase, pending invite, departed member, pause, and closed project. Map an existing project to one task and one deliverable. Preserve original text, timestamps, authors, invitation generations, version numbers, approvals, and reader rights. An accepted v1 result becomes one sealed release. An active v1 decision stays pending for the same human. Map old task, version, decision, and invitation URLs to the corresponding exact subject with a fresh permission check. Make conversion transactional per project and repeatable with unique legacy-source mappings. Serialize conversion with v1 writes, bump the format epoch, and reject stale v1 forms with a reopen link. Verify counts and hashes before enablement. Roll back the feature flag to a compatible reader if needed; a v1 binary alone cannot safely accept writes against converted projects. No live conversion until reviewed and separately approved.

**Code seams.** Extend the existing projects domain with focused plan, task, output, decision, and authorized query modules under `src/lib/projects/`. Keep shared access and actor lookup in one place. Move the catch-all page toward explicit nested project routes with a shared layout. Reuse the current Server Action, safe-return, rate-limit, activity and participation patterns. Extend the strict allowlist for exact routes and query parameters. Feed the same authorized personal work query to Home and Updates. Reuse the public-field account search projection and check project eligibility server-side. Use the existing stack. For the formatted editor, disable raw HTML, restrict link schemes, and render the same saved representation in the reviewer, export and print views. Keep project content and identifiers out of analytics. ## Verification and release evidence

**Software.** Use disposable loopback databases and synthetic accounts. Walk the full workshop as separate browser identities, including a real sign-out and return through a deep link. Also complete a solo project and a one-agent project. Verify a reader, invitee, nonmember connected owner, removed member and new owner see exactly the permitted data on every surface. Check unauthorized references across projects, blocked handoffs, owner pause, closure, invite retries, simultaneous independent saves, duplicate submissions, stale approvals, cycle rejection, missing reviewers, input updates and export after revocation. Package A must export byte-equivalent saved content after package B ships. Check keyboard and phone completion, accessible version differences, large histories, and bounded queries. Run the existing app/auth/Topics-off/relevant analytics suites, typecheck, production build, audit, migration preservation, and both restart checks. Reload a saved draft, a pending human question, a pinned dependency and an approved package across restart.

**Usability.** Put the preview in front of a person who did not implement it. Give them three goals without naming controls: split the work between two teammates, find why the handout is waiting, and identify and export the approved kit. Record the first wrong turn or request for help, fix the interaction and repeat. Screenshots of seeded cards alone do not complete a batch.

**Real agents.** With separate approval for the trial destination and participants, run two independently hosted agents and at least one human. Give them the workshop brief and authorization to work inside Minglo. End each host session after its contribution. For each handoff, record how the host returned, whether the agent independently found the next task and exact input, what it produced, and every human intervention. A neutral reminder to visit is recorded separately from a human relaying content or a link. Inspect the final kit against the original brief and the human’s mid-project decision. Report software readiness, usability observations and host autonomy separately.

## Release boundaries

Ship real planning, multi-person and multi-agent work, versioned outputs, decisions and export in the same release. Native file uploads, cloud-drive editing, calendar writes, paid services, and a hosted model would introduce separate infrastructure and permissions. The release above works with authored documents, pasted notes, labeled source links and local downloads. A future Chief of Staff agent can already participate by proposing a plan, identifying stalled tasks and requesting decisions through its own authorized account. Final approval always requires the designated human’s own authenticated action.
